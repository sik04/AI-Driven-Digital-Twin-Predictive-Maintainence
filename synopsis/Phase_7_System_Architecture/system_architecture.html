7. System Architecture and Workflow

7.1 Architectural Overview and Multi-Tier Decomposition

The IntelliTwin framework is structured around a decoupled, multi-tier cyber-physical research architecture designed to resolve the pervasive gap between data-driven Remaining Useful Life (RUL) estimation, finite-sample distribution-free uncertainty calibration, and sequential operational maintenance decision-making [1]–[3]. In industrial rotating machinery, such as commercial turbofan aircraft engines, standard point predictions optimize symmetric statistical metrics that fail to reflect asymmetric downtime losses (where unscheduled in-service failure penalty significantly exceeds scheduled preventive overhaul cost, CFAIL ≫ CPM) [1], [5]. Concurrently, digital twin implementations in manufacturing literature frequently prioritize high-fidelity 3D geometric visualizations or centralized SCADA dashboards without mathematically formalizing how predictive uncertainty should govern discrete intervention decisions [2], [13], [14].

To bridge these disjoint paradigms, IntelliTwin decomposes asset monitoring, prognostic estimation, uncertainty calibration, and maintenance simulation into five modular, decoupled architectural tiers:

  1. Tier 1: Data Ingestion and Anti-Leakage Preprocessing Tier: Ingests multi-sensor run-to-failure streams from the NASA C-MAPSS corpus, enforces immutable engine-level disjoint split isolation, performs invariant sensor pruning, fits training-only normalization parameters, clusters operational settings, and constructs causal sliding lookback windows [1].
  2. Tier 2: Prognostic Base Inference Tier: Houses complementary shallow gradient-boosted decision trees (HistGradientBoostingRegressor) and deep recurrent neural networks (PyTorch LSTM), generating continuous point predictions of Remaining Useful Life [3], [4].
  3. Tier 3: Hierarchical Conformal Calibration Tier: Computes asymmetric nonconformity scores, evaluates exact engine-weighted quantiles under cluster exchangeability, stratifies calibration bounds across operational flight regimes, and inverts scores into finite-sample prediction intervals [Li(t), Ui(t)] targeting 90% nominal coverage [7], [9].
  4. Tier 4: Sequential Decision and Maintenance Simulation Tier: Evaluates dynamic cycle-by-cycle stopping rules τi = inf{t ≥ W : Li(t) ≤ θ} against conservative lower conformal bounds, tracks economic lifecycle expenditures in Standardized Cost Units (SCU), executes matched-conservatism attribution controls, and conducts 10,000 cluster bootstrap hypothesis tests [5], [8], [12].
  5. Tier 5: Digital Twin Synchronization and Presentation Tier: Formulates a real-time trace-driven state replication engine (TwinReplayEngine) adhering to ISO 23247 principles [14], guarantees strict numerical verification parity (atol ≤ 10−4) against offline batch execution, and exposes streaming REST endpoints via FastAPI to an interactive HTML5/JavaScript operator dashboard [2], [13].

Physical Integration and Research Demarcation

In alignment with rigorous academic reporting standards, the physical integration boundary of the IntelliTwin system is explicitly demarcated:

  • Offline Trace-Driven Simulation: The architecture operates on historical run-to-failure telemetry from the NASA C-MAPSS simulator [1]. No live turbofan engine is physically connected to the host system, and no hardware IoT sensor bus (e.g., MQTT, OPC UA) is claimed.
  • Advisory Decision Support: Maintenance orders dispatched by the simulation tier represent advisory recommendations for maintenance engineers; closed-loop physical actuation (e.g., automatic engine shutdown or thrust throttling) is strictly out of scope.
  • Strict Anti-Leakage Boundary: Held-out test trajectories are isolated from model training, hyperparameter grid search, and conformal score calibration. True failure times and oracle RUL values are revealed exclusively to offline evaluation routines for post-hoc scoring.

7.2 Data Ingestion, Normalization, and Causal Windowing Pipeline

The data pipeline ingests raw continuous multi-sensor records and transforms them into standardized tensor and vector representations while strictly eliminating temporal and inter-engine data leakage.

C-MAPSS Data Schema and Invariant Channel Pruning

The raw C-MAPSS dataset provides 26 columns per cycle: engine unit identifier, cycle index, 3 operational flight condition settings, and 21 thermo-mechanical degradation sensors [1]. Across multi-regime datasets (FD002, FD004), a systematic variance audit identified six invariant or uninformative channels exhibiting zero variance or uninformative responses across all regimes:

Sdropped = { s1 (T2), s5 (P2), s6 (P15), s10 (epr), s16 (farB), s19 (Nf_dmd) }

Excluding these uninformative channels eliminates matrix rank deficiency and numerical instability. The retained schema comprises d = 17 informative channels: 3 operating settings (z1, z2, z3) and 14 dynamic thermo-mechanical sensors (temperatures, pressures, core/fan speeds, fuel ratios, and coolant bleeds).

Strict Engine-Level Split Partitioning

To prevent inter-engine correlation leakage, partitioning is strictly enforced at the engine unit level. For each benchmark dataset, entire run-to-failure engine trajectories belong exclusively to one split:

  • FD001 (Single-Regime Control): 100 total engines split into 50 Training, 20 Calibration, 10 Validation, and 20 Test engines.
  • FD002 (Multi-Regime Primary): 260 total engines split into 130 Training, 52 Calibration, 26 Validation, and 52 Test engines.
  • FD004 (Multi-Regime / Multi-Fault Robustness): 249 total engines split into 124 Training, 50 Calibration, 25 Validation, and 50 Test engines.

Training-Only Normalization and Regime Clustering

Standardization parameters (mean μtrain and population standard deviation σtrain, computed with ddof=0) are derived solely from the designated Training engines:

x̃i(t) = (xi(t) − μtrain) / (σtrain + ε)

where ε = 10−8 prevents division by zero. For multi-regime sub-corpora (FD002, FD004), operating settings (z1, z2, z3) are standardized and clustered into K = 6 operational regimes (C1 to C6) via K-means clustering (K = 6, random_state=2026, n_init=10) fitted exclusively on training data, preserving deterministic centroid ordering.

Causal Sliding-Window Formulation

To preserve temporal causality, feature representations are constructed using a fixed sliding lookback window of length W = 30 cycles with stride 1:

Xi(t) = [ x̃i(t − W + 1), x̃i(t − W + 2), …, x̃i(t) ]T ∈ ℝ30 × 17

For early operational cycles (1 ≤ t < W = 30), the causal buffer is filling; zero padding is strictly forbidden, and prognostic inference is deferred until cycle t = 30. Dual feature representations are constructed from this window:

  • Sequential Tensor: A 2D matrix Xi(t) ∈ ℝ30 × 17 preserving temporal ordering for the recurrent LSTM network.
  • Flattened Vector: A 1D vector vi(t) = vec(Xi(t)) ∈ ℝ510 flattened in C-order (row-major) for gradient-boosted decision trees.

7.3 Prognostic Base Inference Tier

The prognostic inference tier transforms causal window representations into continuous point estimates of Remaining Useful Life ŷi(t).

Dual Target Conventions

During base model training, Remaining Useful Life targets are clamped at an upper threshold Rmax = 125 cycles:

ytrain,i(t) = min(Rmax, Ti − t)

reflecting the empirical physical reality that initial operational wear does not exhibit measurable degradation signatures during early component life [1]. In contrast, during held-out test evaluation, the true uncapped linear degradation target yeval,i(t) = Ti − t is preserved to assess genuine lifetime prognostic accuracy.

Model Architecture Workflows

Two diverse, complementary model families are trained and frozen under Architecture Decision Record ADR-018:

  • HistGradientBoostingRegressor (GBR): Ingests flattened 510-dimensional vectors vi(t). Optimizes the asymmetric pinball loss function Lρ(y, ŷ) = max(ρ(y − ŷ), (1 − ρ)(ŷ − y)) across quantiles ρ ∈ {0.05, 0.50, 0.95} with histogram-binned split finding (max bins = 255, learning rate = 0.05, max leaf nodes = 31, L2 reg = 1.0).
  • PyTorch Deep Bidirectional LSTM: Ingests sequential tensors Xi(t) ∈ ℝ30 × 17. Features two stacked bidirectional LSTM recurrent layers (h = 64 hidden units per direction, 128 concatenated), variational recurrent dropout (p = 0.20), and a LeakyReLU projection head. Optimized using AdamW (η = 10−3, weight decay = 10−4) under Mean Squared Error loss with cosine annealing scheduling.

Point predictions are non-negatively clipped: p̂i(t) = max(0, ŷi(t)). A total of 30 model checkpoints (3 datasets × 2 architectures × 5 seeds [2026..2030]) are registered and frozen.

7.4 Hierarchical Conformal Calibration and Interval Inversion Workflow

The conformal calibration tier converts raw point predictions into statistically guaranteed, finite-sample prediction intervals C1−α(Xi(t)) = [Li(t), Ui(t)] targeting nominal 90% coverage (1 − α = 0.90) [4], [7], [9].

Asymmetric Decision-Aware Nonconformity Scoring

To penalize hazardous overestimation (ŷ > y, risking in-service failure) more heavily than premature underestimation (ŷ < y, resulting in early inspection), nonconformity scores incorporate state-dependent dynamic scaling [7]:

σ(p̂) = (1 + p̂ / 125.0)γ,   z(p̂) = exp(−p̂ / 20.0)
a(p̂) = σ(p̂) · exp(β · z(p̂)),   b(p̂) = σ(p̂) · exp(−β · z(p̂))
si(t) = max( (p̂i(t) − yi(t)) / a(p̂i(t)),   (yi(t) − p̂i(t)) / b(p̂i(t)),   0 )

with candidate parameters γ = 2 and β = −ln 2 ≈ −0.693147, optimized via grid search on the Validation split.

Exact Engine-Weighted Quantile Solver

To resolve the clustered temporal autocorrelation of repeated observations within engines, each observation (i, t) from calibration engine i ∈ {1, …, m} is assigned weight wi,t = 1 / ((m + 1) · ni). Total finite probability mass equals m / (m + 1), with the remaining 1 / (m + 1) assigned to +∞ [9]:

Fdev(q) = (1 / (m + 1)) · ∑i=1..m [ (1 / ni) · ∑t=1..ni 𝕀(si,t ≤ q) ]

The conformal quantile q̂1−α is the smallest observed calibration score satisfying Fdev(q̂1−α) ≥ 1 − α. When calibrating within specific operational flight regimes k ∈ {1, …, K}, condition-adaptive thresholds q̂1−α(k) are computed; if a regime cluster contains fewer than mg ≥ 10 calibration engines, fallback routing to the global threshold q̂1−α(global) is automatically triggered.

Closed-Form Prediction Interval Inversion

Given the calibrated threshold q̂1−α, the finite-sample prediction interval is evaluated via closed-form inversion:

Li(t) = max(0, p̂i(t) − q̂1−α · a(p̂i(t))),   Ui(t) = p̂i(t) + q̂1−α · b(p̂i(t))

where Li(t) represents the conservative lower bound on Remaining Useful Life that directly drives downstream maintenance policies.

7.5 Discrete-Event Sequential Maintenance Utility Simulation Workflow

The simulation tier models asset lifecycle progression cycle-by-cycle using a discrete-event simulator (src/intellitwin/simulator/engine.py) [5], [8].

Sequential Stopping Policy

At each operational cycle t ≥ 30, the simulator evaluates the lower conformal bound Li(t). When the lower bound breaches an operational threshold θ (with default θ = 1.0 cycle), a preventive maintenance order is dispatched immediately:

τi = inf{ t ≥ W : Li(t) ≤ 1.0 }

If τi < Ti, planned maintenance is successfully executed at cycle τi, terminating the trajectory without in-service incident. If the engine reaches its terminal cycle before maintenance is triggered (τi ≥ Ti), an unscheduled catastrophic failure occurs at cycle Ti.

Standardized Cost Units (SCU) Evaluation

Total simulated lifecycle cost for engine i is calculated under the primary reference scenario:

Costi(τi) = CPM + CWASTE · (Ti − τi)   if τi < Ti (Planned Maintenance)
Costi(τi) = CFAIL   if τi ≥ Ti (Unscheduled In-Service Failure)

with economic parameters: planned overhaul CPM = 1.0 SCU, in-service failure penalty CFAIL = 5.0 SCU, and wasted component life penalty CWASTE = 0.20 SCU per cycle.

Controlled Attribution Protocol

To verify that cost reductions stem from genuine uncertainty calibration rather than heuristic over-conservatism, outcomes are evaluated against three pre-registered matched-conservatism control families:

  1. Uniformly Widened Intervals (δ-Widened): q̂′ = q̂ + δ.
  2. Point Safety Margins (Δ-Margin): p̂′(t) = p̂(t) − Δ.
  3. Earlier Scheduled Intervention (θ-Offset): θ′ = θ + τadvance.

Statistical significance is established via 10,000 engine-level cluster bootstrap draws under Bonferroni family-wise error rate control (α = 0.0125) and Two One-Sided Tests (TOST) non-harm equivalence bounds [12].

7.6 Digital Twin State Synchronization and Replay Engine

To translate scientific models into an interactive operational prototype, IntelliTwin implements a real-time trace-driven Digital Twin synchronization engine (TwinReplayEngine) in src/intellitwin/twin/replay.py [2], [13], [14].

Thread-Safe Replay State Machine

The replay engine manages asset state transitions through an explicit lifecycle state machine protected by mutual exclusion locks:

  • WARMING_UP (Cycles 1 … 29): Sensor frames are buffered into the causal history. Inference is deferred; no prediction bounds or maintenance actions are emitted.
  • ACTIVE (Cycles 30 … min(τi, Ti − 1)): The engine maintains the active 30 × 17 sliding window, applies training Z-scores, computes dual GBR/LSTM forecasts, derives conformal bounds [Li(t), Ui(t)], calculates dynamic Health Index HIi(t) = min(1.0, p̂i(t) / 125), and evaluates maintenance policy rules.
  • MAINTAINED (Cycle τi): Triggered when Li(t) ≤ 1.0. The session locks, records a planned overhaul event, and halts further telemetry advancement.
  • FAILED (Cycle Ti): Reached if cycle t attains total failure cycle Ti without intervention. Records catastrophic failure and terminates the session.

Numerical Parity Verification

To guarantee that real-time replay does not introduce numerical artifacts or windowing drift, the replay engine is audited against offline batch execution:

maxt | p̂stream(t) − p̂batch(t) | ≤ 10−4,   maxt | Lstream(t) − Lbatch(t) | ≤ 10−4

Parity is verified across all benchmark datasets via 37 automated pytest modules, establishing that the interactive operator dashboard displays mathematically identical outputs to the scientific evaluation pipeline.

REST API Architecture and Operator Dashboard

The replay engine is exposed via a high-performance FastAPI service (src/intellitwin/twin/api.py):

  • GET /api/health: System health check, runtime metadata, and frozen model registry status.
  • GET /api/catalog: Available benchmark datasets (FD001, FD002, FD004), model families, and test engines.
  • POST /api/sessions: Spawns a stateful replay session for a designated engine unit.
  • POST /api/sessions/{id}/advance: Consumes exactly one cycle observation, returning updated telemetry, predictions, bounds, and maintenance status.
  • POST /api/sessions/{id}/reset: Resets the replay session to cycle 0.
  • GET /api/sessions/{id}/trace.csv: Exports complete cycle-by-cycle operational traces for auditing.

The frontend interface (apps/twin_dashboard/) renders an interactive HTML5/JavaScript cockpit featuring dynamic sensor time-series charts, RUL prediction intervals with confidence bands, gauge dials for Health Index, and visual alert indicators (NOMINAL, ADVISORY, CRITICAL_INTERVENTION).
